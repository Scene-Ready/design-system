# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is the **`@scene-ready/design-system` package** for Scene Ready (sceneready.tech — software for Fire, EMS, and Search & Rescue). It is documentation + brand assets distributed as a git-installed npm package, not an application:

- `BRANDING.md` — the authoritative spec (~600 lines) covering brand identity, color palette, typography, spacing, components, dark mode, and accessibility.
- `tokens.css` — the canonical, machine-readable design tokens (CSS custom properties). Downstream Scene Ready apps import this file via `@scene-ready/design-system/tokens.css`; `BRANDING.md` is the prose that describes how to use them.
- `assets/` — official logo SVGs (`scene-ready-brandmark.svg`, `-icon.svg`, `-appicon.svg`, reversed variants for dark backgrounds) and `favicon.ico`. The brandmark's text is outlined (paths, not `<text>`), so it renders without any font loaded.
- `tailwind.css` — the Tailwind CSS v4 theme (`@theme inline reference`) that maps Tailwind's colours, fonts, sizes, radii, shadows and easing onto `tokens.css` variables. Apps on Tailwind import it instead of copying values. When a token is added, renamed or removed, update it here and in `emails/tokens.js`, then run `npm run build:emails` and `npm run check`.
- `fonts/` — self-hosted Barlow, Barlow Condensed and JetBrains Mono (woff2 + `fonts.css`), generated by `scripts/vendor-fonts.mjs` from pinned Fontsource packages. Don't hand-edit; change `FAMILIES` and rerun `npm run vendor-fonts`. Never point an app at Google Fonts or another font CDN. Email is the one exception: mail clients fetch fonts over the network, so the email wrappers link Google Fonts (README, Fonts).
- `emails/` — the themed email wrappers. Their MJML lives in `scripts/email-source.js` and is compiled to `emails/compiled.js` by `npm run build:emails` (committed; the wrappers never run `mjml`, so they work in Workers). Rebuild after changing a template or `emails/tokens.js`.
- `package.json` — declares the package as `@scene-ready/design-system` with `exports` for `./tokens.css`, `./assets/*`, and `./BRANDING.md`. Marked `private: true` so it is never published to the public npm registry.
- `README.md` — consumer-facing install + usage docs.

Consumers install from git (a `codeload.github.com` tarball URL pinned to a tag; see README). There is no build system for consumers; `npm run check` is the test suite (it includes `vitest run`). `tokens.css` is the artifact; the only runtime JavaScript is the email wrappers and `bin/scene-ready-brand-assets.js`, which copies the seven parent-brand files into an app's static root (keep its file list in sync with `assets/`) and replaces `<root>/fonts/` with `fonts/`. Common tasks are editing `BRANDING.md`, adding/updating assets, or bumping a token value.

**When you change a token value, you must also bump `version` in `package.json` and tag the commit (`git tag vX.Y.Z`)** so consumers can pin to the new release.

## Working in this repo

**`tokens.css` is the canonical source for token *values*; `BRANDING.md` is the canonical source for token *usage*.** Downstream apps import `tokens.css`. When asked to build a UI component, page, or snippet, reference token names — never hardcode hex codes or px values.

**Prefer semantic aliases over primitives whenever a value should change between light and dark mode.** `tokens.css` defines two layers: primitives (`--navy-700`, `--gray-50`, `--space-4`) and semantic aliases (`--bg-page`, `--text-primary`, `--border`, `--accent`, `--focus-ring`, `--success-fg`, etc.). The aliases follow the OS color scheme, and `data-theme="dark"` or `"light"` overrides it (BRANDING.md §9.4); primitives don't change. Use `--bg-card` for a card background, not `--white`. Use `--success-fg` for status text, not `--success`.

**If you change a token, update both `tokens.css` and any per-section table in `BRANDING.md` that quotes the value inline.** The component spec tables (Buttons, Form Inputs, Cards, etc.) often quote hex codes and pixel values directly; grep the doc before committing a token change to catch every occurrence.

**Logo assets must stay in sync with the inline SVG in `BRANDING.md`.** The "SVG Icon Mark (inline use)" block in BRANDING.md and the files in `assets/` are the same artwork — if one is updated, update the other. Do not introduce new logo variants without a corresponding entry in the Variants table.

**Brand-color rules that are easy to violate:**
- Navy and Red are brand colors only — never use them as status colors. Status uses the semantic palette (success/warning/danger/info).
- Red 700 (`#C8102E`) is for accents, CTAs, and active states only — never large background fills.
- Dark mode does not invert brand colors. Red **text** lifts to Red 300; red **fills** (primary button) stay Red 700; Red 500 is decorative only. See the dark-mode table (BRANDING.md §9.4).
- Status text uses `--*-fg` on `--*-surface`. Dots, bars, icons and borders use `--*-mark`, which lifts in dark mode. The base tones (`--success` …) fail AA as small text and fall under 3:1 on dark surfaces; they're for fills that don't change with the mode (the danger button).
- Uppercase text uses `--tracking-caps` (0.05em) or `--tracking-eyebrow` (0.1em), never a literal.
- `--text-tertiary` is for placeholders and decorative text only; timestamps use `--text-secondary`.

**Dark values live in `[data-theme='dark']` only.** The `prefers-color-scheme` block below it in `tokens.css` is generated by `npm run sync-dark`; `npm run check` fails if they differ. The `dark:` variant in `tailwind.css` must keep the same rule (dark under `[data-theme='dark']`, or OS dark with no `data-theme='light'` ancestor).

**Contrast is checked.** `npm run check` fails if any token pairing drops below its WCAG 2.2 minimum in either mode, or if a ratio in BRANDING.md §8 doesn't match its colors. When you change a color, run it, and fix the table from the computed value.

**Voice rules for any UI copy you generate:** active voice, fire/EMS/SAR terminology ("On Duty", "Crew", "Apparatus"), no "Oops!"/"Uh oh!" — this is software used during emergencies. Error messages must be specific and actionable.
